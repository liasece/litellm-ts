# 提交更改

## 两种模式

- **普通提交**（“提交”“commit”“提交本次改动”）：检查工作区，按明确路径暂存属于本次任务的改动，再提交。不因暂存区为空而停止。
- **仅暂存模式**（用户明确说“只提交暂存内容”“只提交 staged changes”）：只提交已有 index，不新增 `git add`；此模式下暂存区为空才停止并报告。

模式无法从用户原话唯一确定时，按普通提交执行，并在结果中说明实际暂存了哪些文件。

## 约束

- 只暂存能够确认属于本次任务的路径，用 `git add -- <明确的文件列表>`。禁止 `git add -A`、`git add .`、`git add -u`、`git add -f` 及其他无法审计范围的写法。
- 不修改代码，不格式化，不回滚，不 `amend`，不重写历史，不 stash、restore、reset、clean。
- 保留工作区中用户和其他 Agent 的 staged、unstaged 与未跟踪修改。同一文件既有本次改动又有归属不明的并发修改、无法隔离时，报告该路径并停止该文件的提交。
- 不暂存或提交 `.env`、凭据、Token、私钥、连接串等敏感内容，不强制添加被 ignore 的文件；因此排除的路径要在结果中说明。
- 不自动 push，不执行部署或生产发布；只有用户另行明确要求时才执行。
- 不为提交而运行会读取整个工作树的测试或构建。项目门禁按 `AGENTS.md` 的验证与交付要求执行；用户当轮明确要求验证时从其要求。
- 即使改动包含多个修改部分也可以提交；正文必须准确表达每个主要修改部分。
- 遵守当前对话和 `AGENTS.md` 关于 `git commit` 的授权要求；没有明确提交授权时不得提交。

## 提交信息

- 使用中文。
- 格式：`<type>: <简要描述>`。
- `type` 只能用 `feat`、`fix`、`refactor`、`docs`、`chore`。
- 根据最终 staged diff 的主要意图选择一个最准确的 `type`，不要只根据文件数量判断。
- 正文可选；需要时用多条 `-` 说明关键变更。
- 如果 staged 内容包含多个修改部分，正文必须用多条 `-` 分别列出，覆盖所有主要修改类别。
- 修复 issue 时，仅在能够确认 issue 编号时于末尾添加 `Closes #<number>`。
- 禁止添加 `Co-Authored-By` 等署名。

## 流程

1. 确认目标仓库路径：优先使用用户指定路径；否则使用当前工作区。
2. 普通提交先运行 `git -C <repo> status --short`，结合本轮对话确定属于本次任务的路径；仅暂存模式跳过此步。
3. 普通提交先从文件名排除敏感与被忽略路径，再阅读授权范围内的 diff，确认暂存范围。需要理解已有 index 时查看 `git -C <repo> diff --cached --stat` 或针对性的 `git -C <repo> diff --cached -- <path>`。
4. 普通提交执行 `git -C <repo> add -- <明确的文件列表>`；用户指定文件或任务范围时只暂存该范围，未限定范围时暂存本次任务全部可提交改动。仅暂存模式不执行 add。
5. 复核最终范围：`git -C <repo> diff --cached --stat`，必要时查看针对性 staged diff。没有可提交改动时，仅暂存模式停止并报告；普通提交说明没有可提交内容并停止。
6. 根据最终 staged diff、对话上下文和仓库近期提交风格编写提交信息。只有在确有必要时，才运行 `git -C <repo> log -5 --oneline` 辅助判断风格。
7. 运行 `git -C <repo> commit -m "<提交信息>"`；需要正文时追加独立的 `-m` 参数，复杂正文可用消息文件配合 `git commit -F` 保留真实换行。
8. 运行 `git -C <repo> status --short`，确认提交结果，同时不得改变剩余工作树。
9. 成功后报告提交哈希、提交标题、实际暂存的路径和仍然存在的 unstaged/untracked 状态；如果运行环境要求 Git directive，必须一并输出。

## 失败处理

- `add` 或 commit 失败时，报告失败原因、已执行到哪一步和剩余工作；保留当前工作区与 index，不自动撤销暂存。
- 不自动修复代码、不扩大暂存范围、不绕过 hooks、不自动重试破坏性命令。
- hooks 修改文件或导致失败时，保留现场并报告，不把 hook 产生的内容加入暂存区。
