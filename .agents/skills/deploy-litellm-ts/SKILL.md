# 部署 LiteLLM TS

以当前仓库说明和生产现场为准，完成单点 LiteLLM TS 服务的发布闭环。不要复制 Samba 已同步的源码，不要泄露密钥，不要中断仍在执行的数据库迁移。

## 每次从现场重新建立事实

1. 完整读取仓库当前的 `AGENTS.md`。若其中内容与本 Skill 不同，以 `AGENTS.md` 为准。
2. 检查用户当前请求是否明确授权部署。仅检查、诊断或解释状态时，不得自行重启服务。
3. 检查工作区和暂存区，但只读取与本次任务有关的状态。保留用户或其他任务的修改，不执行 `reset`、`restore`、`clean`、暂存或提交。
4. 从 `AGENTS.md` 和现场命令重新确认远程主机、仓库路径、Node.js 路径、部署入口、容器名称和验证契约，不把本 Skill 中的历史示例当成永远不变的配置。
5. 记住本地仓库是远程仓库的 Samba 映射。禁止使用 `scp`、`rsync` 或其他源码同步步骤。

## 执行发布前验证

至少执行 `AGENTS.md` 当前要求的基础检查：

```sh
git diff --check
node node_modules/typescript/bin/tsc --noEmit
```

根据改动范围补充验证：

- 前端改动：只对相关文件运行 ESLint，并运行能验证可观察行为或明确回归风险的测试。
- 后端或 Logs 查询改动：按 `AGENTS.md` 选择聚焦 Jest 或完整后端测试。
- 不为了“有测试”而添加只复述静态配置、类名或实现细节的断言。
- 前端独立类型检查若受仓库既有夹具阻塞，以当前 `AGENTS.md` 指定的发布门禁为准。
- Samba 共享的 `node_modules` 若出现 macOS/Linux 原生依赖错配，先确认依赖实际由哪一端安装，再在匹配的平台运行测试；不要直接删除锁文件或整个依赖目录。

任何必需检查失败时，先诊断并修复根因，再从相关检查重新开始。不得带着未解释的失败进入生产部署。

## 执行正式部署

从当前 `AGENTS.md` 读取并执行正式部署命令，不调用本 Skill 自带脚本，也不重新实现部署流程。

观察并区分部署阶段：

1. 后端 TypeScript 构建。
2. Next.js 生产构建。
3. Docker 镜像构建与完整性校验。
4. 生产数据库只读预检。
5. 停止并删除旧容器。
6. 启动新容器并执行迁移。
7. 等待健康检查。

长时间运行时持续提供简短进度，不因暂时没有输出就判定失败。只有部署命令完成且上线核验通过后，才能报告部署成功。

## 形成自愈闭环

发生失败或长时间无进展时，按以下顺序循环：

1. **定位阶段**：确认失败发生在验证、构建、镜像、数据库预检、容器替换、迁移、健康检查还是外部入口。
2. **收集事实**：读取当前进程、进程组、CPU、等待点、最近生成文件、容器状态、OOM、重启次数、有限范围日志和数据库活动。
3. **保护可用状态**：确认旧容器是否仍健康、是否已经进入替换阶段、是否存在活动迁移事务。
4. **修复根因**：只修改本次任务范围内能够解释失败的代码或配置。不要用重复重启掩盖构建、依赖、网络或迁移问题。
5. **重新验证**：从受影响的最小验证开始，再执行全部发布门禁。
6. **重新部署并核验**：仅在根因已修复且生产状态允许时重试。

需要具体诊断信号和安全停止条件时，读取 [故障诊断参考](references/troubleshooting.md)。

若修复需要新的权限、改变部署基础设施、删除数据或扩大用户原始任务范围，应停止并请求用户决定，不得以“自愈”为由扩大授权。

## 执行上线核验

按当前 `AGENTS.md` 逐项执行，不依赖固定脚本：

1. 确认生产容器仍在运行、健康、未 OOM，且没有异常重启。
2. 在有限日志范围内确认数据库接管、健康路由注册和网关启动标志。
3. 验证外部健康入口和 Logs 页面均返回 HTTP 200。
4. 使用容器现有的 master key，在容器内部请求 `/spend/logs/ui`；不得打印 key、环境变量或 Authorization 内容。
5. 验证认证查询返回 HTTP 200、预期行数，并且每行都有 `session_total_count`。
6. 对前端视觉改动，在真实浏览器中验证部署后的可观察行为。涉及对齐和尺寸时，跨多行测量实际几何或计算样式，不以搜索压缩产物中的类名代替页面验证。
7. 对 Logs 查询或迁移改动，执行 `AGENTS.md` 要求的索引计划、性能或迁移检查。

任何一项失败都回到“形成自愈闭环”，不得只报告部署脚本已经结束。
