# 运维 LiteLLM TS 生产服务

以用户本轮授权、当前仓库事实和生产现场为准。不要复制 Samba 已同步的源码，不要泄露凭据，不要
中断仍在执行的数据库迁移。

## 先确定授权模式

1. 完整读取仓库根 `AGENTS.md`。
2. 根据用户原话选择且只选择一种模式：
   - **只读诊断**：检查状态、核验部署结果、查看日志、解释失败或调查卡住。只允许读取，不得运行
     部署入口、重启/停止/删除容器、写生产数据或修改基础设施。
   - **部署变更**：用户明确要求部署、发布或重启 LiteLLM TS。允许执行标准部署入口及完成该次发布
     所必需的非破坏性核验。
3. Bug 修复、代码修改、检查线上状态或“看看部署是否成功”都不隐含部署授权。若请求含义不足以确定
   是否允许生产变更，停在只读事实并请求用户决定。
4. 部署授权不包含 commit、push、手工数据库写入、标准脚本之外的容器重建、基础设施变更、数据删除
   或扩大任务范围；这些动作分别需要明确授权。
5. 部署失败后，只有当修复代码已在用户授权的修改范围内时才实施修复。否则完成诊断、保护现场并
   请求方向，不把“自愈”解释为无限制改码授权。

## 重新建立当前事实

1. 部署或完整生产诊断前，读取 [生产运维与故障诊断参考](references/troubleshooting.md)。只读小范围
   检查可读取其中与目标有关的章节。
2. 按以下优先级裁决冲突：用户本轮范围与授权 → 当前源码和 `package.json` → 标准部署脚本及主机
   当前配置 → 容器、进程、日志和数据库活动 → reference 中的已知拓扑。
3. 在执行生产变更前，现场确认远程主机、仓库目录、Node.js 工具链、标准部署入口、验证容器、生产
   容器和外部入口。reference 中的值只用于定位，不得替代现场确认。
4. 若文档与现场不一致，先使用只读证据确定事实。无法唯一确认安全入口或工具链时停止，不猜测路径、
   版本或容器名，也不创建替代流程。
5. 检查工作区和暂存区，只读取本次任务需要的状态；保留用户和其他任务的修改，不执行清理、回滚、
   暂存或提交。

## 只读诊断

1. 只收集回答当前问题所需的有限状态、日志和指标；不要输出环境变量或认证内容。
2. 区分验证、构建、镜像、数据库预检、容器切换、迁移、健康检查和外部入口阶段，避免把“暂时无
   输出”或单一 `unhealthy` 状态直接判为失败。
3. 按 reference 中的信号判断是否仍有构建或迁移活动。只要迁移事务仍活跃、容器仍运行且未 OOM，
   不得停止、删除或重启容器。
4. 报告观察到的事实、最可能阶段、尚缺证据和下一项需要授权的动作；只读请求到此结束。

## 部署前门禁

仅在“部署变更”模式执行：

1. 从当前 `package.json` 和受影响目录的 `AGENTS.md` 选择发布门禁；至少执行 `git diff --check`、
   后端 TypeScript 检查以及覆盖改动的测试。根据风险补充完整后端 build/test 和前端 ESLint、
   Vitest、TypeScript 检查、Next.js production build。
2. 测试只验证可观察行为和真实契约。不要新增复述静态配置、类名或实现细节的断言。
3. 若 Samba 共享依赖发生平台错配，在匹配的平台运行检查；不要删除锁文件或整个依赖目录。
4. 任何必需门禁失败时，先诊断。只有失败修复属于当前授权范围时才修复并重跑；否则停止部署并报告。

## 执行部署

1. 使用 reference 指向并经现场确认的唯一标准部署入口。不要重新实现部署流程，不要手工拼接
   `docker run`，不要在验证容器内运行宿主机部署脚本。
2. 观察并区分构建、镜像、数据库预检、旧容器切换、新容器启动/迁移和健康检查阶段。长时间运行时
   提供简短进度，不因没有新输出就重复启动第二次部署。
3. 若旧生产容器缺失，标准脚本应把它视为无需停止并继续；不要创建占位容器。脚本不支持该分支时，
   先诊断并按授权边界决定是否修复，不在脚本外重建服务。
4. 若失败需要新权限、改变基础设施、写生产数据、执行破坏性恢复或扩大范围，保护当前可用状态并请求
   用户决定。

## 失败处理

1. 先定位失败阶段并收集有限证据，再保护旧容器、活动迁移和其他可用状态。
2. 使用 reference 对照构建卡住、容器缺失、迁移超时和平台依赖错配等已知分支；不要用重复重启掩盖
   构建、依赖、网络或迁移问题。
3. 修复在当前授权范围内时，从受影响的最小检查开始，再重跑全部发布门禁和标准部署；不在范围内时
   报告根因与安全下一步并请求授权。
4. 无法证明停止、重启或恢复动作安全时不执行。不得以“自愈”为由扩大权限或任务范围。

## 上线核验

部署命令结束不等于发布成功。按 reference 的当前核验契约完成：

1. 确认生产容器运行、健康、未 OOM 且没有异常重启。
2. 读取有限范围启动日志，确认服务和数据库迁移已经进入可服务状态。
3. 验证外部健康入口和 Dashboard 入口。
4. 验证本次改动对应的真实可观察行为。涉及 Logs 查询时，再执行带认证的 Logs 契约检查；涉及视觉
   改动时，在真实生产页面验证，不以构建成功或压缩产物文本代替。
5. 任一必需核验失败时回到诊断流程；不得只报告部署脚本已结束。

- 容器健康、OOM、重启与外部入口状态；
- 对目标行为完成的生产核验；
- 失败根因、采取的安全恢复措施、未验证项和仍需用户授权的动作。

禁止在回复、命令摘要或日志摘录中展示密钥、数据库连接串、认证头或部署脚本中的敏感内容。
