前端性能调查与优化方案

01 · Executive summary

先给出判断

1000 行页面从进入路由到最后一个数据行可见约 1.95s，期间出现 1,256ms 的长任务；滚动到列表底部也能产生 125–284ms 的长任务。把行数降到 100 后，首屏约 0.56s、DOM 从 66,914 降到 7,130。行数与 DOM / 组件数近似线性，说明问题在“全量渲染”而不是某个单点格式化函数。

已落地方向：保留 1000 行的分页能力，但只渲染视口附近的行；第一阶段已在日志表启用 opt-in 虚拟滚动，并适配生产 Dashboard 的 .application-main 内层滚动容器。生产 1000 行页面只挂载 27–33 个数据行、约 2.8k 个 DOM 元素；URL、筛选和深链接抽屉保持原契约。行级 view model 与轻量 tooltip 属于第二阶段，未在本轮实施。

03 · CPU profile

主线程在忙什么

对 1000 行首次渲染做 Chrome CPU profile。除了浏览器原生布局/绘制（(program)）之外，最大的一项不是业务格式化，而是 UiTable 的滚动尺寸测量触发的强制布局；随后是 GC、Vue 组件实例化和每行时间格式化。

为什么测量会这么贵

可单独优化

UiTable 在 onMounted、ResizeObserver 和 rows / columns / loading 的 watcher 中调用 measureScroll()。它读取 scrollWidth / clientWidth / scrollLeft，在 1000 行、6.7 万 DOM 上每次读取都可能迫使浏览器同步布局。

这不是唯一根因，但属于低风险、可独立拿到的收益：合并到 requestAnimationFrame、只观察必要节点、值没变不写回，就能避免重复布局。真正把 1000 行成本压下来的仍是虚拟化。

数据层不是这次的主因：列表页的 page 是 shallowRef，不是把 1000 行全部变成深层响应式；API 列表投影排除了 messages / response / proxy_server_request 大字段；profile 中 zod 解析约 3ms、shareLogRows 约 2ms。先重写接口或改数据库通常拿不到这次的收益。
04 · Root causes

四个叠加的结构性成本

R1 / DOM

所有行一次性挂载

UiTable 的 #row 插槽对全部 visibleRows 做 v-for，日志表把 1000 条数据直接交给它；没有窗口化、没有分片。表里每一行都是真实 DOM。

R2 / COMPONENTS

每个单元格都是一个重组件

12 列 × 1000 行 = 12,000 个 LogsTableCellComponent。每个实例都会注入价格 store，并创建约 16 个 computed（价格、状态、session、模型、token、TTFT、TPS、路由、标签、tooltip 等），不管当前列是否用到。

R3 / OVERLAYS

约 8,300 个 tooltip / popover 包装器

request ID、session、key、token 等用 UiTooltip 包一层，成本和模型用 UiPopover；时间和状态则直接渲染文本。每个包装器都有自己的 setup、ref、事件和 onUpdated hook，放大挂载与更新成本。

R4 / LAYOUT & GC

布局、滚动测量和分配压力

6.7 万元素、12,000 个内联宽度样式、固定表格布局，使布局/绘制本身很重；measureScroll 强制同步布局，GC 采样 147ms 也说明短命对象很多。

补充：localLogTime 每行调用 new Date().toLocaleString(...)，profile 占 40ms；formatPrice 占 18ms。这些是容易拿的“小钱”，但不是 1.95s 的主因。把 1000 行限制成 500 行只能把问题减半，不能把曲线变平。
05 · Options

候选方案与取舍

按“是否能消除全量 DOM”排序。推荐把虚拟化作为主方案，其余作为配套或过渡。

A

窗口化 / 虚拟滚动 + 行级 view model 推荐

只挂载视口附近 30–50 行，上下用 spacer 行维持滚动高度；数据、筛选、分页、URL 语义不变。再把每行重复计算收敛一次，普通 tooltip 改为轻量实现。这是唯一能让 1000 行与 100 行的 DOM 成本接近的方案。

DOM -85–95%改动中等 / 收益最大
B

分批渲染 / content-visibility 过渡

先渲染 100 行，空闲时继续追加；或对行加 content-visibility: auto。能改善首次长任务和部分绘制，但最终 DOM 仍会到 6.7 万，内存和后续交互成本仍在，不能作为 1000 行的最终解。

首屏部分改善改动小 / 上限低
C

限制每页 500 / 改成无限加载 产品取舍

把 1000 选项拿掉或默认 200，是最快的止血；但用户失去一次查看 1000 条的能力。若 1000 行主要用于审计/导出，更合适的是提供导出，而不是在页面渲染 1000 行。

立即止血产品能力受限
D

只做 formatter 缓存 / measureScroll 合并 配套

把 Intl.DateTimeFormat、金额 formatter 缓存起来，合并滚动测量，减少重复布局。低风险，但只覆盖约 10–25% 的首屏时间，不改变 12,000 个单元格的事实。

10–25%低风险 / 必做配套
E

服务端 keyset + 无限滚动 长期

如果以后要浏览远超 1000 条的历史，可把“一页 1000 行”改成 keyset 游标 + 增量加载。它与虚拟化互补，但对当前的 1000 行问题不是必需的第一步，且会扩大 API/产品改动面。

可扩展范围大 / 非当前必需
06 · Recommended plan

建议按三个阶段落地

不要先做大规模重构再验证。先用一个可回退的 opt-in 虚拟化把曲线压平，再用行级模型和轻量 tooltip 拿第二段收益；每一步都能独立发布、独立回滚。

PHASE 0 · 0.5–1 天

低风险止血

不改变 DOM 结构，先减少明显浪费。

  • 合并 measureScroll 到 rAF，避免在挂载/观察回调中重复强制布局；值未变化不写回。
  • 缓存 Intl.DateTimeFormat 和金额格式化器；避免每行创建 formatter。
  • 建立 1000 行基准脚本，记录首屏、DOM、长任务，作为后续对照。
PHASE 1 · 2–4 天

虚拟化行（主方案）

只改表格渲染层，保留数据与 URL 契约。

  • 给 UiTable 增加 opt-in 的 virtual / rowHeight / overscan，默认关闭，先只让日志表启用。
  • 窗口滚动方案：沿用页面滚动，按表体位置计算可见区间；上下 spacer 行维持总高度。
  • 固定行高 33px（现有 CSS 已是固定高度），过扫 8 行；resize / 数据变化时钳制范围。
  • 保留 request_id key、点击、键盘、横向滚动、深链接抽屉；补充 aria-rowcount 和 spacer 的 aria-hidden。
PHASE 2 · 1–2 天

单元格与 tooltip 收敛

让虚拟化后的每行也更轻。

  • 每行计算一次 LogsRowView（时间、状态、模型、token、成本、session、hash 等），单元格只消费结果。
  • 按列拆分单元格，避免 16 个无关 computed 都挂到每个单元格上。
  • 普通文本用轻量 title 或表格级事件委托；仅 token / feature / cost / model 保留富浮层，并延迟到交互时挂载。
// 目标：调用方只增加 opt-in 参数，数据/URL/抽屉语义不变 <UiTable :columns="tableColumns" :rows="data" row-key="request_id" virtual :row-height="33" :overscan="8" fixed-layout manual-sort > <template #row="{ row }"> <LogsTableRowComponent :log="row" ... /> </template> </UiTable> // 表体只渲染窗口内的行；spacer 行只承担高度，不进入读屏/交互 <tr aria-hidden="true"><td :colspan="colspan" :style="{ height: topSpacer + 'px' }"></td></tr> <LogsRow v-for="row in windowRows" :key="row.request_id" ... /> <tr aria-hidden="true"><td :colspan="colspan" :style="{ height: bottomSpacer + 'px' }"></td></tr>
第一阶段的实现顺序已按此执行：先加 opt-in 开关和窗口计算，再迁移日志表；没有把 UiTable 改成默认虚拟化。日志表行高已经是 33px（.ui-table td），适合固定行高窗口化；手机端仍保留横向表格，不改现有布局。第二阶段的行级 view model 和轻量 tooltip 尚未开始。
07 · Implementation & production verification

第一阶段已经上线，行数与 DOM 的线性关系被切断

实现边界很窄：UiTable 增加默认关闭的虚拟化选项，日志表显式开启；数据、分页、URL 查询参数、筛选和深链接抽屉都不改。上线核验时发现生产页面的滚动不在 window，而在 .application-main 内层，因此补充了“最近的纵向滚动祖先”识别和对应的内层滚动回归测试。

代码改动

  • UiTable.vue：新增 virtual（默认 false）、rowHeight、overscan；用上下 spacer 行保持 tbody 总高度，只渲染窗口内的数据行。
  • 窗口计算抽成纯函数 UiTableVirtualLogic.ts；滚动测量按 requestAnimationFrame 合并，并复用 ResizeObserver 处理标签页隐藏/显示。
  • 自动寻找最近的纵向滚动祖先；生产实测为 .application-main，不是 window。窗口滚动与内层滚动共用同一套相对可视区计算。
  • LogsTableComponent.vue 启用 virtual、row-height="33"、overscan="8"；保留 request_id key、点击、深链接和全部列行为。

生产核验结果

  • 页面参数保持 logs_page_size=1000；列表接口返回 1000 行、分页总数约 7k（随时段变化）。
  • 首次进入：27 个数据行、1 个 spacer、2,812 个 DOM、325 个表格单元格；表格高度 33,032px，滚动范围未丢。
  • 滚动到内层容器底部：数据行 33 个，顶部 spacer 31,911px，可视区内 25 行，首行已切换；没有一次挂载 1000 行。
  • 状态筛选可以应用并清除；点击数据行会写入 log= 深链接并打开详情抽屉，关闭后清除参数。
  • 390px 视口下页面宽度保持 390，横向滚动留在表格内部；纵向滚到底部仍只挂载 32 行，首行已切换。
  • 部署容器健康、OOMKilled=false、RestartCount=0；外部健康入口与 /ui/?page=logs 均返回 200。
本地合成数据基准（1000 行，最终实现复测）：首行可见 347ms；DOM 从 66,914 降到 1,986；数据行 24 个；tooltip/popover 锚点从 8,338 降到 168；初始最长长任务从 1,256ms 降到 73ms；滚到底部 67ms，滚动后挂载 30 行。生产读数受登录、接口、实时刷新和数据量影响，因此这里不把本地毫秒数当作生产 SLA。
验证覆盖：5 个纯窗口计算用例；3 个 Playwright 日志表用例（窗口滚动、标签页往返、内层滚动容器）；既有日志筛选、URL 深链接、抽屉和会话行为测试继续通过。完整组件套件中，两个会话时间线的既有基线失败仍按原样单独记录，不能归因于本次表格改动。
取舍不变：原生 Ctrl+F 只能命中当前挂载的行；日志页仍以 Request ID 筛选作为权威查找方式。行高必须保持固定；当前不支持 bodyMaxHeight 与 virtual 的组合。第二阶段的行级 view model 和轻量 tooltip 尚未实施。
08 · Acceptance criteria

怎么证明真的变快

性能优化不能只看“感觉”。下面保留可重复的 1000 行基准口径，并给出这一轮在本地合成数据和真实生产页面上的结果；生产页面只做结构与行为核验，不用登录和网络耗时冒充渲染指标。

本轮结果

  • 1000 行时只挂载 24 行、1,986 个 DOM 元素，低于 8k 上限
  • 首行可见 347ms（本地合成数据，目标 < 0.7s）
  • 初始最长长任务 73ms；没有出现 > 500ms 的单个任务
  • 从顶部滚到底部 67ms，滚动后只挂载 30 行
  • 生产 1000 行页面挂载 27–33 行，URL、筛选和深链接保持
  • 100 / 500 / 1000 三档曲线未在本轮重跑；不把单档结果外推为三档结论

必须同时守住的契约

  • 默认 12 列、最多 18 列的显示与横向滚动不变
  • request_id 筛选、分页、排序、时间范围、URL 回填不变
  • 点击行打开详情、J/K 切换、session 时间线、深链接刷新恢复
  • live tail 更新后滚动位置不跳、选中行不丢
  • 键盘可达、aria 行数/表头语义正确；spacer 不被读屏
  • 移动端 390px 仍无页面级横向溢出
本轮用的是临时 Playwright 基准（固定视口、合成数据、关闭 live tail），不作为 CI 硬门槛；日常门禁仍跑日志筛选、深链接、抽屉和会话行为测试。后续可把该基准固化成独立性能脚本，用宽松阈值避免 CI 抖动。
09 · Risks & product notes

需要提前说清楚的取舍

浏览器 Ctrl+F 只能找到已挂载行虚拟化后原生页内查找不再覆盖全部 1000 行。日志已有 request_id 表头筛选，应把它作为查找入口；如审计依赖 Ctrl+F，需要在方案评审时确认。
固定行高假设当前 td 为 33px 且 nowrap；若未来 badge/错误信息允许换行，窗口高度会失真。需要保留“行高变化则回退到非虚拟/动态测量”的开关。
无障碍与表格语义spacer 行必须 aria-hidden；总行数用 aria-rowcount 表达；键盘焦点进入屏幕外行时要先滚入视口。不能只做视觉窗口化。
live tail 与滚动位置1000 行 + 默认 10s live tail 会周期性替换数据。虚拟化后只补视口，但仍要验证“读者正在看的位置不被拉走”，沿用现有滚动位置策略。
UiTable 是多页共用组件把虚拟化做成 opt-in，先只接日志页；其他实体表继续走原路径，降低一次性回归面。测试要覆盖默认关闭时的行为不变。
产品是否真的需要 1000 行同屏本轮保留了 1000 行/页的浏览能力，但不再全量挂载；如果后续确认用户主要用导出/审计，可以再下调默认 page size，虚拟化不需要因此回退。
