现象与影响链

11-15 03:59–04:01Z，模型组 commandcode/deepseek/deepseek-v4.1-flash 经 opencode-go 走 aresponses 流式：上游只看到占位符，模型把占位符原样写进工具参数，网关没有换回原文，Agent 拿到 ssh {{EMAIL_2wgytxs6}} … 并实际执行，ssh 把主机名判为非法。

请求体→ 调度点脱敏
明文 → 占位符→ opencode-go
原生 Responses 流→ 响应写入器
模式锁定为 passthrough→ 客户端拿到占位符
unresolved = 0

统计只记录「看到了占位符但查不到原文」；整条流没进还原器时，这个计数不会增长，所以监控此前完全无感。

根因

PrivacyResponseWriter 在第一次 res.write 时解析一次模式并锁定整条响应。原判定顺序是：只要 context.hasReplacements 为 false 就返回 passthrough。

Responses 协议入口会在发往上游之前先写出 response.created / response.in_progress 等首帧；此刻请求体还没脱敏，token 表为空。首帧把模式锁成 passthrough 后，后续所有帧（包括已含 token 的正文）都原样写回，还原器从未运行。

修复前探针捕获到的帧（{{EMAIL_ossjvd5w}} 正是该请求自己的映射）：

event: response.output_text.done
data: {"type":"response.output_text.done", …, "text":"ssh root@{{EMAIL_ossjvd5w}} 'echo ok'"}

另一处独立缺口：Responses 的推理正文（response.reasoning_text.delta/.done）与内容分片（response.content_part.*）不在改写范围内，即使模式正确，思考过程里仍会残留 token。

修复

位置改动原因
PrivacyResponseWriter.resolveMode SSE 判定提前到 hasReplacements 之前；无替换时 SSE 分片仍原样直通以保持成本；非 SSE 保持原逻辑。 首帧可能早于脱敏完成；模式不能按「此刻有没有替换」锁定。
SseRewriter._rewriteResponses 新增 reasoning_text.delta/.done 与 content_part.added/.done 的还原；reasoning_text.done 前补发 carry。 推理与分片同样是客户端可见内容，且会被部分客户端写回历史。
PrivacyResponseWriter 告警 已脱敏却解析成 passthrough 时记录一条 warn（只带路径、内容类型、字节数）。 同类回归不再静默。
测试与文档 新增 5 个写入器测试（首帧早于脱敏、跨帧切开、未知 token、gzip 透传、直通成本）与 2 个推理还原测试；更新 docs/privacy-redaction.md。 锁定「SSE 不依赖替换状态」这一契约。

遗留问题

历史会话里的占位符无法还原。映射表只在单个请求的内存里存在，从不落库；泄漏期间写进客户端历史的 {{EMAIL_2wgytxs6}} 没有反向表可查。修复后这些请求会以「未还原」计数暴露出来（部署后窗口内已看到若干真实流量 unresolved 2–4），但网关无法替客户端还原。

  • 受影响的 Agent 会话需要人工清理：把历史里的 ssh {{EMAIL_…}} 等改回真实值，或直接开新会话。
  • 可选加固（需另行确认）：请求体里出现「形如占位符但不在本次映射」的文本时，是否统一替换成中性占位（如 [REDACTED_EMAIL]），避免模型把模板当变量回显。
  • 监控口径：unresolved > 0 现在能反映真实未还原；但仍无法区分「历史残留」与「本请求异常」，后续可在事件里拆分来源。
