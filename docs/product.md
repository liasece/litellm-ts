# LiteLLM TS 产品文档

这份文档回答「为什么做这个网关、服务谁、什么算做对、哪些理解是错的」。当你要判断一个需求是否属于产品意图、某个能力该不该存在、或者需要向没参与过讨论的人解释这个项目时看它。产品意图只从用户原话取证，代码和旧文档只能说明现状，不能反过来定义需求。

## 定位与边界

一句话定位：**公司内部统一模型网关 + 管理面板**。所有 AI 客户端只配一个入口，就能访问多家上游模型和多份订阅套餐；费用、日志、账号、路由和协议兼容在同一个后台治理。

- 服务对象是公司内部使用 AI 的开发与运营人员。语料里用户始终以「我们」指代公司，没有出现过对外售卖、第三方租户或按量结算给外部客户的要求。
- 交付形态是单实例服务：「我们是单点服务，不用考虑集群问题。我们采用一次性全量部署，接受服务停机。」（2026-07-27）这条决定了产品不做高可用、灰度、多副本一致性，代价是有秒级不可用窗口。
- 它不替代上游供应商的账号体系。DeepSeek、MiniMax、GLM、MiMo、LLMux 等直连供应商，以及 Codex、Claude、Kimi、Antigravity、xAI、CommandCode、OpenCode Go 七家订阅，账号本身仍在上游侧，网关只做调用、路由、计费与审计。
- 它也不是「数据不出本机」的合规产品：请求仍然到达上游供应商，脱敏只是把敏感值换成占位符（见[隐私脱敏](privacy-redaction.md)）。

## 什么算做对

用户没有写过验收标准，但从他反复提出的要求里可以推出五条判断：

- **客户端只改一次配置**：新增一个模型、换一个上游、加一份订阅，使用方不需要改客户端或重新发版。
- **费用数字能解释**：页面上的花费能与供应商账单对上；对不上的部分必须能归因到峰谷价、折扣、保证金或自定义价格，而不是「大概就是这样」。
- **事后能复盘**：任意一条请求都能在 Logs 里找到上下游报文、路由与 fallback 轨迹、耗时分解和费用，包括进行中的请求。
- **上游故障不等于网关故障**：单个供应商超时、限流、鉴权失败要么被 fallback 掉，要么原样透传给客户端，不污染网关自身的错误率与冷却判定。
- **界面上没有假装可用的东西**：没有后端支撑的入口不出现；接口返回空就显示空，不显示假成功（这条直接来自 2026-11-08 的清理要求）。

## 设计理念与取舍

- **正确性优先于性能**。「我觉得没有必要做这个内存缓存，每个请求都直接查数据库应该也不花什么时间？」「那就全面重构，正确性优于性能。」（2026-07-27）配置改动必须立刻生效，所以运行时配置走逐请求读库 + 仓库层缓存，而不是散落在进程里的长 TTL 快照。后续性能优化只能在保住这条语义的前提下做。
- **展示层不造数据**。「前端不应该聚合。session 应该只在点击 log 后的详情页中显示该 session 的所有 log。」（2026-07-27）同理，正在进行中的请求 token 显示「无数据」而不是 0；图表少于两个有效数据点就不画线。
- **服务端日志只记自己的错**。「服务器日志应该只记录自身的逻辑错误，不需要将上游错误视为服务器错误。」（2026-11-01）上游 5xx、429 是业务分支，要走 fallback 或原样透传，不能污染错误率与冷却判定。
- **没有后端支撑的入口一律删除**。2026-11-08 用户把这条说成原则：「MCP Servers、邮件/告警/CloudZero 这些『假成功』页面可以删除」，并要求「连 drizzle/ 迁移一起清」，但保留「`/v1/embeddings`、`/v1/completions`、`/v1/moderations`、`/v1/audio/*`、`/v1/files` 还要对外承诺」。判定依据与逐项清单见[无用功能清理记录](cleanup-candidates.md)。
- **同类东西只实现一次**。「不要一个窗口实现N遍，应该复用组件」「任何一个显示了模型名字的地方都应该有图标」（2026-07-27、2026-11-10）。这条演化成了前端 `features/platform` 的平台层与会话里反复出现的「触类旁通，检查所有类似问题」。
- **成本可比较**。用户要的不只是账单，而是「同样的月用量，谁花钱更少？」这类采购判断：页面必须覆盖全部品牌而不是最便宜的若干个，并显示需要买几个什么档位的账号（2026-11-08～11-10）。
- **代价要被说出来**。接受停机、接受手机端日志页仍是桌面表格、接受订阅号池的冷却等待——这些是有意选择的代价，写在能力边界里，而不是当成待修缺陷。

## 能力与明确不做的事

当前对外承诺的推理面：`/v1/chat/completions`、`/v1/messages`、`/v1/responses`、`/v1/completions`、`/v1/embeddings`、`/v1/moderations`、`/v1/audio/*`、`/v1/images/*`、`/v1/files*`（Anthropic Files 转发）、`/v1/search/tools`、`/v1/models`。

管理面按 Dashboard 导航分四组（`ui/litellm-dashboard/src/features/application/data/NavigationData.ts`）：

- **AI GATEWAY**：Virtual Keys、Playground、Models + Endpoints、Search Tools。
- **OBSERVABILITY**：Usage、Logs、Speed、Privacy。
- **ACCESS CONTROL**：Teams、Internal Users、Organizations。
- **SETTINGS**：Built-in Capabilities、Router Settings、Subscriptions、Logging & Alerts、Admin Settings、Cost Tracking。

明确不做：多租户 SaaS 与对外计费；集群、灰度和跨副本一致性；MCP 执行、Guardrails、Prompts、Vector Store、Caching 管理面（2026-11-08 清理）；SSO/SCIM 管理面；Agent/A2A/沙箱。语义缓存与自动分类路由目前只是[上游对齐记录](upstream-alignment.md)里的候选建议（F37、F08），没有执行链，不算已承诺能力。

## 常见误解

这些都来自用户纠正 agent 的会话，值得在需求评审时先排除：

1. **「订阅就是运维单独装的 CLIProxy 服务」**——错。CLIProxy 的 Go 子进程已被移除，订阅在 LiteLLM 进程内执行、只保留兼容管理入口。依据：`AGENTS.md` 的订阅运行时一节与 2026-11-10「把这个 Go 子进程也去掉」。
2. **「订阅账号的 key 可以在模型页随便填」**——错。订阅凭据只在订阅账号页维护，模型只选择暴露哪个上游模型；普通供应商才走凭据字段。
3. **「日志列表可以按 session 聚合展示」**——错，会直接违背上面「展示层不造数据」；session 只在详情页展开。
4. **「脱敏等于数据没出公司」**——错，脱敏是发往上游前的替换，上游依然收到请求（可能是被替换后的内容）。
5. **「页面上的费用等于供应商账单」**——不完全等。落账口径含折扣、保证金与自定义价格，历史日志不回溯重算。
6. **「手机端适配要重排列表」**——对日志页被明确撤回：2026-11-13 要求「logs 页面列表改回一开始没有适配手机的样子」，代价是该页在手机上靠横向滚动。
7. **「测试越多越好」**——错。用户要求「不要有那种不满足我们公司价值观的测试用例」，见 `AGENTS.md` 的测试质量一节。
8. **「流式请求失败时，下游能靠 HTTP 状态码判断原因」**——错。SSE 一旦开始写出，状态行就固定为 200，失败只能以协议内的错误帧收尾；此时 `error.code` / `error.type` 是下游判断「429 限流可重试」还是「真故障」的唯一依据。2026-11-16 由请求 `3ff51003` 暴露：上游 429 在 `/v1/responses` 流里被压成 `server_error`，客户端因此不按限流退避重试。分类逻辑统一在 `src/core/api/ClientErrorCode.ts`，三条流式入口（Responses、chat SSE、Anthropic messages）共用，不要再各自硬编码错误码。
9. **「文字里写了『Try again in N seconds』，客户端就知道等多久」**——错。那句话是给人看的，SDK 的退避与自动重试只读 `Retry-After` 头。同一个冷却时长必须同时进文案和响应头：`ApiError.retryAfterSeconds` 由 Router 的 `cooldown_time`（或上游自带的 `Retry-After`）换算，`sendProtocolError` 统一下发；无冷却条目时文案回退默认冷却时长，响应头也必须跟着回退，不能缺席。流式请求没有第二个响应头可用，退避提示只能靠错误帧里的分类，因此错误码与 `Retry-After` 是同一件事的两半，改一处必须想另一处。
10. **「日志里 Key 列为空是正常现象」**——错，那是主密钥流量。主密钥不是虚拟密钥，没有 token 行和别名，`SpendLogs` 只留下它的哈希；不补标签时整批主密钥请求在面板上无法归属（2026-11-16 排查 `be8a1263` 时，近 24 小时 8,147 条即此情况）。读侧按哈希标记为 `Master Key`（[spendLogKeyIdentity.ts](../src/spend/spendLogKeyIdentity.ts)），既不回写历史行也不伪造虚拟密钥身份；若要从根上区分调用方，应改用虚拟密钥而非主密钥。

## 待确认问题

- 是否有对外（非公司内部）提供推理服务的计划？语料只有内部使用，若要做，多租户、计费与合规都需重新定义。
- OpenRouter 等第三方聚合商是否要接入？2026-11-08 用户只要求研究其可靠性，未表达接入意图。
- 「同样的月用量，谁花钱更少」的套餐数据由谁维护、多久核对一次？目前是管理员填写，程序不查询供应商价格。
- Ollama 的产品定位：前端 provider 目录里有 Ollama / Ollama Chat，后端没有对应 provider 分支（见[开发文档](development.md#已知缺口与待确认)）。是要基于 OpenAI 兼容路径支持，还是应当从目录移除？
